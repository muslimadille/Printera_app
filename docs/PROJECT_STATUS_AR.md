# حالة المشروع والبيزنس — Printera (cct.printera-app)

> ملف بالعربي بيشرح المشروع بيعمل إيه، البيزنس بتاعه، والمرحلة الحالية —
> وبالتحديد: **هل الـ Backend والداتابيز اتبنوا ولا لأ؟**
> الملفات التقنية (الأركيتيكشر والـ Specs) بالإنجليزي: `ARCHITECTURE.md` و `docs/backend-laravel/`.

---

## 1. المشروع بيعمل إيه؟ (نظرة عامة)

**Printera** هو تطبيق ويب **SaaS لتسعير أعمال الطباعة والتغليف** موجّه للمطابع
(الشركات اللي بتطبع كروت، علب، مجلات، أكياس… إلخ). فكرته إنه بيحوّل شيتات الإكسيل
اللي المطابع بتحسب بيها التكلفة والتسعير إلى نظام منظّم فيه **حاسبات متخصّصة** لكل
نوع شغل، مع حفظ عروض الأسعار وإعدادات الأسعار لكل عميل.

الواجهة **عربية بالكامل (RTL)**، والتطبيق شغّال حاليًا كـ **نسخة بيتا** (المسار
`/app` بس هو المتاح للعامة).

### القيمة الأساسية
المستخدم بيدخل:
- **نوع الورق وسعره** (بالطن أو بالرزمة) والجرامية والمقاسات.
- **مواصفات الشغلانة**: مقاس الطباعة، الكمية، عدد ما يفصل في الشيت، عدد الألوان،
  الأوجه، السلفان، التكسير (Die Cut)، القالب… إلخ.
- **أسعار الطباعة والفرز والتشطيبات** (ورنيش، يوفي، فويل، بصمة… إلخ).

والتطبيق بيحسب **التكلفة النهائية وسعر القطعة** (بنفس منطق معادلات الإكسيل بالظبط)،
وبيطلع **عرض سعر** جاهز، وينفع يتصدّر PDF/Excel.

## 2. الوحدات (الحاسبات والمزايا)

التطبيق فيه حوالي **٤٠ تاب/حاسبة** مقسّمين لمجموعات:

- **حاسبات تكلفة الأصناف:** حساب الصنف (hybridengine)، تكلفة صنف (itemcost)،
  مسطح (flat)، حساب التكلفة (costcalc)، المحرك الذكي (smartengine)،
  دمج أصناف (mergeitems)، حاسبة التسعير (calculator).
- **القوالب والعلب (Die-Cut / Packaging):** Die Cut 1–5، علبة بيد (Carrying Handle)،
  Lid-Tuck، علبة دواء (Medicine Box)، 10001، الرصّ التلقائي (SVG Auto-Nesting)،
  وقوالب D001 / D003 / T0001 / T0002 / A01010000 / A01700000 وقالب عام.
  دي **محرّكات هندسية بارامترية** بترسم شكل العلبة (2D SVG) + **معاينة ثلاثية الأبعاد
  (Three.js)** + **رصّ تلقائي على الشيت** + تصدير PDF/SVG.
- **المونتاج:** مونتاج (montage)، مونتاج قالب (templatemontage)، MONTAG.
- **المجلات:** تكلفة مجلة (magazinesheet)، المجلات، المجلة، المجلات (قديم).
- **الأكياس:** حساب الأكياس (bagcalc). و**العلب والأكياس** (boxpricing).
- **أدوات:** التكاليف المحفوظة (savedquotes)، الإعدادات (أسعار)، أنواع الورق،
  التشطيبات، استيراد تسعيرات بالجملة، عرض سعر، إدخال الموظف.
- **الأدمن:** المستخدمين (users)، السجل (loginhistory).
- **الدليل:** guide.

كمان في **إدخال صوتي بالعربي** (VoiceInput) بيتحوّل لحقول في الحاسبة عن طريق
ذكاء اصطناعي (Gemini عبر بوابة Lovable).

## 3. مين بيستخدم التطبيق؟ (الأدوار)

في **٣ مستويات مستخدمين** (تفصيلها التقني في `docs/backend-laravel/01-ROLES-AND-PERMISSIONS.md`):

1. **الأدمن (Admin):** إدارة المنصّة (طرف Printera/Sanabil). بيتحكم في كل الحسابات،
   بيشوف سجل الدخول وتحليلات الاستخدام لكل مستخدم، وبيحدّد الاشتراك (تاريخ الانتهاء)
   وعدد الأجهزة المسموحة وعدد الموظفين.
2. **صاحب الحساب (Account Owner):** المطبعة العميلة. بيملك بياناته وعروضه، وبيقدر
   **ينشئ موظفين** (في حدود العدد المسموح)، ويتحكم في **صلاحيات التابات** لكل موظف،
   ويسمح/يمنع الموظفين من رؤية عروضه.
3. **الموظف (Employee):** مستخدم تابع لصاحب حساب. بيرث صلاحيات صاحب الحساب وقت
   الإنشاء، وبيشوف عروض زمايله و(اختياريًا) عروض صاحب الحساب.

التحكم في المزايا بيتم عن طريق **صلاحيات التابات لكل مستخدم** (كل تاب ليه مفتاح
تشغيل/إيقاف لكل مستخدم).

## 4. المرحلة الحالية — إجابة سؤالك بالظبط

### الفرونت إند (الواجهة)
**ناضج جدًا وشبه مكتمل.** فيه حاسبات ضخمة ومعقّدة، محرّكات هندسة وتغليف، معاينة
3D، رصّ تلقائي، تصدير PDF/Excel، إدخال صوتي، ونظام صلاحيات كامل. متبني بأدوات حديثة
(React + TypeScript + Vite + Tailwind + shadcn/ui)، وأصله اتعمل على **Lovable**
وبعدين اتظبط يدويًا. الحالة: **بيتا شغّالة**.

### الـ Backend والداتابيز — **اتبنوا فعلًا، لكن على Supabase**
- **آه، الـ Backend والداتابيز موجودين وشغّالين** — بس على **Supabase** مش Laravel:
  - **الداتابيز:** Postgres على Supabase، فيه **٨ جداول** جاهزة (المستخدمين،
    الجلسات، أحداث الجلسات، سجل الدخول، أحداث النشاط، العروض المحفوظة، الإعدادات،
    صلاحيات التابات). الـ schema **مستقر** (٢٠ migration، آخر تعديل ٨ يونيو ٢٠٢٦).
  - **الـ API:** كله في **Edge Function واحدة اسمها `manage-users`** (~١٣٠٠ سطر،
    ~٤٠ أكشن) شغّالة بـ service-role. + فانكشن تانية للإدخال الصوتي.
  - **المصادقة:** نظام **مخصّص** (مش Supabase Auth): يوزرنيم + باسورد (bcrypt)،
    وتوكنز جلسات مخزّنة في جدول، مع حدود أجهزة وطرد جلسات و heartbeat.
  - **التخزين:** bucket خاص (`montage-files`) بروابط موقّعة.
  - **الأمان:** كل الجداول مقفولة (deny-all RLS)، والوصول كله من خلال الفانكشن.

- **اللي لسه مش موجود:**
  - **مفيش Laravel API** لحد دلوقتي (ده الهدف الجديد).
  - **مفيش تطبيق موبايل** — والـ API الحالي RPC (أكشنات) مش REST منظّم، فمحتاج
    إعادة تشكيل عشان يخدم الموبايل.
  - **مفيش لوحة تحكم Admin منفصلة** كـ backend مستقل — الأدمن دلوقتي مجرّد تابات
    جوّه نفس تطبيق الويب.

### الخلاصة
> **الـ Backend والداتابيز اتبنوا بالفعل — بس على Supabase.**
> المطلوب دلوقتي: **إعادة بناء الـ Backend كـ Laravel API (بمصادقة JWT)،
> وإزالة Supabase بالكامل، وتجهيز الـ APIs عشان تخدم تطبيق موبايل**، مع
> **لوحة تحكم Admin**. ده اللي الـ Specs في `docs/backend-laravel/` بتخطّط له.

## 5. القرارات المتفق عليها للـ Backend الجديد

- **Laravel** كـ REST API تحت `/api/v1`، بيحل محل Supabase بالكامل.
- **مصادقة JWT** (توكن) + **سجل جلسات في الداتابيز** عشان نحافظ على حدود الأجهزة
  وطرد الجلسات والـ heartbeat زي ما هي.
- **نموذج الهوية زي ما هو بالظبط:** يوزرنيم + باسورد بس، **بدون إيميل**
  (استعادة كلمة المرور بتتم عن طريق الأدمن/صاحب الحساب).
- **نفس الـ ٣ مستويات** (Admin / صاحب حساب / موظف) + نظام **صلاحيات التابات**.
- **التوثيق التقني إنجليزي، وملفات البيزنس والحالة عربي.**

## 6. الخطوات الجاية (باختصار)

1. بناء Laravel API يوصل لـ **تطابق كامل** مع سلوك `manage-users` (نفس الجداول
   ونفس الرسائل العربية).
2. تحويل الفرونت إند لاستخدام الـ API الجديد **من غير ما نلمس مكوّنات الواجهة**
   (بنغيّر بس طبقة الاتصال في `src/lib/userApi.ts`).
3. التحقق من التطابق endpoint-by-endpoint، ثم **نقل البيانات والملفات**.
4. تشغيل الفرونت على Laravel، **حذف Supabase** نهائيًا.
5. تجهيز **لوحة تحكم الأدمن** و**APIs جاهزة للموبايل**.

التفاصيل الكاملة والمراحل في:
`docs/backend-laravel/00-OVERVIEW-AND-MIGRATION-PLAN.md`.
